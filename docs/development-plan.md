## 1. تعريف المنتج

**Maintenance Request Management System** هو Backend API يمكّن الموظف من إنشاء طلب صيانة ومتابعته، ومسؤول الصيانة من إدارة الأنواع وتعيين الفنيين، والفني من تحديث حالة الطلب حتى الحل والإغلاق.

### الأدوار

| الدور | المسؤوليات |
|-------|-----------|
| `Employee` | إنشاء طلباته ومتابعتها |
| `Technician` | استعراض الطلبات المسندة إليه وتحديث حالاتها ضمن الصلاحيات المسموحة |
| `MaintenanceAdmin` | إدارة أنواع الصيانة، استعراض الطلبات، إسناد الفنيين، إدارة المستخدمين، تنفيذ العمليات الإدارية المسموحة |

### التقنيات الأساسية

- C# و.NET 8
- ASP.NET Core Web API باستخدام Controllers
- Onion Architecture بأربعة مشاريع: API / Application / Domain / Infrastructure
- SQL Server وEntity Framework Core Code First Migrations
- **نظام مصادقة مخصص** (Users/Roles/UserRoles) — **بدون ASP.NET Core Identity**
- **BCrypt.Net-Next** لـ Hashing
- **System.IdentityModel.Tokens.Jwt** و**Microsoft.AspNetCore.Authentication.JwtBearer** لـ JWT
- **Guid v7 (Sequential)** للمفاتيح الأساسية
- CQRS وMediatR
- FluentValidation وMediatR ValidationBehavior
- Redis لتخزين قائمة أنواع الصيانة النشطة مؤقتًا (بعد نجاح النسخة الأساسية)
- xUnit للاختبارات الآلية
- ملفات HTTP أو Postman للاختبار اليدوي

### خارج نطاق هذا المشروع

- RabbitMQ, SignalR, Hangfire, Serilog, Docker
- Microservices
- واجهة Frontend
- **Refresh Tokens** (مؤجلة كـ Future Enhancement)
- **Permissions دقيقة (Fine-grained)** — الأدوار كافية
- **التسجيل العام** — Admin فقط يُنشئ المستخدمين
- **Email Confirmation / Password Reset عبر البريد**
- **External Login (Google, Facebook, ...)**

## 3. طريقة إدارة المهام

### حالات المهمة

- `Backlog` — لم يبدأ العمل عليها.
- `In Progress` — قيد التنفيذ.
- `Blocked` — متوقفة بسبب اعتماد أو مشكلة.
- `Review` — انتهى التنفيذ وتحتاج مراجعة ذاتية.
- `Done` — تحققت معايير القبول ووُثّق التغيير.

### قواعد العمل العامة

1. ابدأ من `MS-001` وتحرك حسب الترتيب والاعتماديات.
2. لا تعتبر المهمة مكتملة لمجرد أن الكود يبني؛ يجب تجربة السلوك المتوقع.
3. كل ميزة يجب أن تشمل مسار النجاح وحالة فشل واحدة على الأقل.
4. لا تضع منطق الأعمال في Controller.
5. لا تثق في `UserId` أو `Status` إذا أرسلهما العميل وكان المفترض أن يحددهما النظام.
6. لا تضف Abstraction أو Generic Repository بلا حاجة واضحة.
7. بعد كل مهمة، حدّث README أو ملف الطلبات إذا تغير سلوك النظام.
8. استخدم Commit صغيرًا واضحًا بعد اكتمال وحدة عمل منطقية.
9. **لا تنتقل إلى الميزة التالية قبل تحقق معايير قبول الميزة الحالية.**
10. **لا تستخدم ASP.NET Core Identity بأي شكل؛ النظام المصادقة مخصص بالكامل.**
11. **عند أي غموض معماري، ارجع إلى الوثائق المرجعية.**

### Definition of Done — متى نقول إن المهمة انتهت؟

- [ ] الكود موجود في الطبقة الصحيحة.
- [ ] المشروع يبني دون أخطاء.
- [ ] جُرّب سيناريو النجاح.
- [ ] جُرّب سيناريو فشل أو صلاحية غير مسموحة.
- [ ] لا توجد أسرار أو كلمات مرور داخل Git.
- [ ] عُدّل التوثيق أو ملف HTTP عند الحاجة.
- [ ] يمكن شرح سبب التصميم، وليس فقط وصف ما يفعله الكود.

## معيار الجودة العام — Clean Code & Business Logic

هذه المعايير تنطبق على كل مهمة، حتى لو لم تُكرر جميعها حرفيًا في وصفها.

- **Clean Code:** أسماء واضحة، دوال مركزة، تجنّب التكرار والتعقيد غير الضروري.
- **SOLID:** طبّق المبادئ عندما تحسّن التصميم؛ لا تحوّلها إلى قواعد شكلية.
- **Business Logic:** قواعد العمل في Domain، تنسيق حالة الاستخدام في Application.
- **Layering:** Controllers للـ HTTP، Handlers للتنسيق، Domain للقواعد، Infrastructure للتفاصيل.
- **Validation:** FluentValidation لفحص المدخلات؛ لا تستبدل قواعد المجال.
- **Security:** لا تثق في بيانات العميل الحساسة. تحقّق من الصلاحيات وملكية المورد.
- **Errors:** أعد أخطاء متسقة، لا استثناءات عامة.
- **Persistence:** async وCancellationToken، تجنب استعلامات غير ضرورية.
- **Maintainability:** لا abstraction إلا بحاجة واضحة.
- **Review:** سيناريو نجاح + سيناريو فشل قبل Done.

### بوابة مراجعة الجودة لكل مهمة

- [ ] أستطيع شرح لماذا وُضع الكود في هذه الطبقة.
- [ ] لا توجد Business Rules داخل Controller.
- [ ] تم رفض حالة غير مسموحة.
- [ ] لا توجد ثقة ببيانات حساسة من العميل.
- [ ] الكود مفهوم ولا يحتوي abstractions غير مبررة.
- [ ] جُرّب السلوك يدويًا أو آليًا.

**الأولوية:** P1
**الاعتماد:** MS-045

### المطلوب

- [ ] إنشاء `MaintenanceSystem.Tests` باستخدام xUnit.
- [ ] إضافة مراجع المشاريع المطلوبة.
- [ ] ضبط أسماء الاختبارات.
- [ ] إضافة أمر تشغيل الاختبارات إلى README.

### معايير القبول

- يمكن تشغيل `dotnet test` بنجاح.
- لا يعتمد مشروع الاختبارات على تفاصيل داخلية غير لازمة.

### مراجعة جودة التنفيذ

- [ ] الاختبارات تقيس السلوك المتوقع لا تفاصيل التنفيذ الداخلية.
- [ ] لا يوجد اعتماد على Redis أو SQL Server في اختبارات الوحدة البسيطة.

## MS-047 — اختبار انتقالات حالة طلب الصيانة

**النوع:** Unit Testing / Domain
**الأولوية:** P0
**الاعتماد:** MS-046 وMS-002

### المطلوب

- [ ] اختبر انتقالات الحالات المسموحة.
- [ ] اختبر رفض انتقالات غير مسموحة.
- [ ] اختبر أن الحالة وبيانات الإسناد لا تتغير عند الرفض.

### معايير القبول

- اختبارات للحالات الناجحة والمرفوضة.
- لا تحتاج قاعدة بيانات.
- تُثبت أن قواعد الانتقال مطبقة داخل Domain.

### مراجعة جودة التنفيذ

- [ ] الاختبارات تغطي حدود القاعدة.
- [ ] لا تُخفى الأخطاء بعبارات `catch`.

## MS-048 — اختبار Validators وApplication Handlers

**النوع:** Unit Testing / Application
**الأولوية:** P1
**الاعتماد:** MS-046 وMS-009 إلى MS-034

### المطلوب

- [ ] اختبر Validator واحدًا على الأقل لكل مدخلات حرجة.
- [ ] اختبر حالات مثل عدم وجود نوع صيانة نشط.
- [ ] استخدم mocks/fakes.
- [ ] اختبر أن Handler لا يتجاوز قواعد Domain.

### معايير القبول

- تمييز بين خطأ المدخلات ورفض Business Rule.
- يمكن فهم سبب الفشل.
- لا تعتمد على خدمات خارجية حقيقية.

### مراجعة جودة التنفيذ

- [ ] لا يتم تقليد كل dependency بلا حاجة.
- [ ] الاختبارات لا تكرر تنفيذ منطق الإنتاج.

# قواعد لا تتجاوزها أثناء التنفيذ

- **لا تستخدم ASP.NET Core Identity بأي شكل.**
- **لا تبدأ Redis قبل أن تعمل قراءة أنواع الصيانة من SQL Server.**
- **لا تبدأ تعقيد CQRS قبل أن تفهم مسار Command/Query/Handler.**
- **لا تخلط Validation مع Business Rules.**
- **لا تعتبر JWT وحده كافيًا؛ افحص ملكية الطلب أيضًا.**
- **لا تسمح للعميل بتحديد هويته أو دوره أو حالة الطلب الأولية.**
- **لا تضف مشروعًا أو مكتبة جديدة إلا إذا كان لها دور واضح.**
- **لا تنتقل إلى المهمة التالية إذا كانت المهمة الحالية لا تعمل أو لم تُختبر.**
- **لا تنشئ جدول MaintenanceRequest قبل MS-025.**
- **لا تنشئ جميع الجداول مسبقًا.**
- **كل Migration جديدة تطور المخطط الحالي ولا تعيد بناءه من الصفر.**
- **لا تكشف User Enumeration في رسائل Login.**
- **لا تخزّن كلمات المرور كنص عادي.**
- **لا تسمح لـ Admin بتعطيل نفسه أو تغيير دوره.**
- **لا تُشغّل Seeder في Production.**
- **لا تضف Generic Repository أو AutoMapper أو Unit of Work فوق EF Core.**
- **الدوال السلوكية في Domain، لا في Handler أو Controller.**
- **عند أي غموض معماري، ارجع إلى الوثائق المرجعية.**

# Future Enhancements (خارج النطاق الحالي)

- Refresh Tokens + Token Rotation.
- Permissions دقيقة (Fine-grained).
- Email Confirmation / Password Reset عبر البريد.
- External Login (Google, Microsoft, ...).
- 2FA.
- Audit Log لتغييرات الأدوار.
- Cache لـ SecurityStamp لتقليل استعلام DB.
- MaintenanceRequestHistory لتتبع انتقالات الحالة.
- RowVersion لمنع التحديثات المتزامنة.
- Soft Delete للمستخدمين.
- Rate Limiting على Login.
